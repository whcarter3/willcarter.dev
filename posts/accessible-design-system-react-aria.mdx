If you have ever tried to build a fully accessible dropdown menu by hand, you know it is one of those tasks that looks like an afternoon and turns into a month. Keyboard navigation, focus management, the right ARIA roles and states, screen reader announcements that make sense, and behavior that holds up across browsers and assistive tech. Each piece is doable. All of them together, correctly, for every component in a product, is a different scale of problem. At Moment, we built our design system on React Aria specifically so we would not have to solve that problem from scratch over and over.

Here is the core idea behind React Aria, and the thing that made it click for me. It separates behavior from presentation. React Aria, from Adobe, gives you the hard part, the accessibility and interaction behavior of a component, as a set of unstyled hooks and components. It does not give you a single pixel of styling. You bring the look. It brings the years of accumulated knowledge about how a combobox is supposed to behave for someone using a keyboard, a screen reader, a touch device, or a different language.

That split sounds academic until you feel the weight of what it removes. Take a modal dialog. The visible part, a box with a backdrop, is trivial. The accessible part is not. When the dialog opens, focus needs to move into it. While it is open, focus needs to stay trapped inside, so tabbing does not wander off into the page behind it. Escape should close it. When it closes, focus needs to return to the element that opened it, not jump to the top of the page. Screen readers need to know a dialog appeared and announce it correctly. None of that is visible, all of it is required, and all of it is the kind of thing that is quietly broken in a depressing number of shipped products. React Aria handles it, and we got to spend our time on how the dialog looked and felt instead of relitigating focus management for the hundredth time.

A combobox is an even better example, because it is deceptively deep. Typeahead. Arrow keys moving through options. The right announcements as the highlighted option changes. Handling the difference between hovering an option and having it selected. Closing on the right events and staying open on others. Doing all of this on a phone as well as a laptop. I have built comboboxes the hard way, and I have built them on React Aria, and there is no contest in terms of how much behavior you get correct on the first try.

But picking a good foundation is not the same as having a design system, and I want to be clear about the difference, because this is where the systems thinking comes in. A design system is not a folder of components. It is a contract. It is the agreement that a button means a specific thing, looks a specific way, behaves a specific way, and exposes a specific set of options, everywhere in the product, no exceptions. The components are how you enforce the contract, but the value is the consistency and the shared language, not the code itself.

So on top of React Aria's behavior, we built the layers that made it ours. Design tokens, so color, spacing, typography, and the rest came from a single source instead of being retyped as magic numbers in a hundred files. A composition model, so components could be combined predictably instead of every team inventing its own one-off variants. Documentation, because a design system nobody understands is just a second codebase to maintain. The goal was that a developer reaching for a component got accessible, on-brand, consistent behavior by default, without having to think about any of it.

That phrase, by default, is the whole point. The reason accessibility so often ships broken is that it is treated as a finishing step, a thing you bolt on at the end if there is time, audited once and then quietly eroded by the next feature. That approach loses every time, because there is never time at the end. The only version that works is the one where doing the normal thing, grabbing the standard component, gives you an accessible result automatically, and where you would have to go out of your way to build something inaccessible. React Aria let us make accessibility the path of least resistance instead of a tax on good intentions.

If I were starting a design system today, I would make the same call. Not because React Aria is the only good option, there are others in the headless, behavior-first family, and the right choice depends on your stack and constraints. I would make it because the behavior-versus-presentation split is the correct way to think about the problem. Let a focused library carry the accessibility and interaction logic that is hard and rarely worth reinventing, and spend your own effort on the things that make your product yours: how it looks, how it feels, and the contract that keeps it coherent as it grows.
